* TODO Handle room-not-existing on client — no heartbeat, can't detect a gone room :p2:runtime:
:PROPERTIES:
:ID:       quackster-7
:END:


The client checks room existence exactly ONCE, on mount, via api.room.exists(code) (src/routes/room/[code]/+page.svelte). After that there is no heartbeat or keepalive. If the room dies server-side mid-session (server restart, room evicted, task panic), the client may keep a half-open WebSocket and never receive another snapshot — it never detects the room is gone and just hangs.

Server side also has a gap: when the room task exits, the broadcast sender drops and state_rx.recv() in ws.rs returns Err — the write_task currently just breaks silently. There is no explicit 'room ended/closed' message sent before teardown, so the client has nothing to react to.

Fix is two-sided:
- Client heartbeat: ping/pong or a no-op interval; if no snapshot/pong within a window, declare the room gone, toast, clearRoom, route home.
- Server room-gone signal: emit an explicit message before the room task exits so clients get a clean reason rather than a silent stream end.
Files: src/lib/room.svelte.ts, src/routes/room/[code]/+page.svelte, api/src/game/room.rs, api/src/http/ws.rs

* TODO Parallelize YAML data loading with rayon :p3:runtime:
:PROPERTIES:
:ID:       quackster-11
:END:


Loading is fully sequential today. Two parallelism surfaces in api/src/data/loader/mod.rs:

1. Per-file parse: load_yaml_dir does `files.iter().map(parse_file).collect()` — each file is read_to_string + serde_yaml::from_str independently. rayon par_iter drops in here cleanly. Biggest win: file IO + YAML decode are the expensive parts, and parse_file already returns Parsed<T> without touching shared state.

2. The 5 kind loads (questions, packs, tags, games, overlays) in load_dataset are independent of each other and could run concurrently too, but the per-file win dominates since most kinds have many files.

On the "parse into a Vec instead of a HashMap to parallelize" idea: collect_registry already folds a Vec<Parsed<T>> into the HashMap sequentially, so this is structurally already true here — the registry/dedup step is the sequential tail, rayon parallelizes the parse step that feeds it. No need to restructure the registry into a Vec; the dedup-by-id pass must stay sequential anyway (it needs the map to detect duplicates).

Caveat: dataset is ~20 questions now, perf irrelevant at this scale. Worth doing only if/when content grows (hundreds+ files) or boot latency shows up. Profile before optimizing.

Files: api/src/data/loader/mod.rs (load_yaml_dir, load_dataset, parse_file)
Spec: docs/data-model.md §Validation (runs at server start).
